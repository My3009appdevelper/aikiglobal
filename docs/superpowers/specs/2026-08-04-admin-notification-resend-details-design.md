# Admin Notification Resend And Details

## Scope

Improve manual notification administration without adding database tables:

- Use the Aiki mark as the default Android FCM notification icon.
- Open a detail page when an admin taps a dispatch card in Historial.
- Show delivery-attempt, inbox, open, and read metrics with precise labels.
- Allow completed and partial manual dispatches to be resent as new dispatches.
- Allow failed zero-success dispatches to be retried through the existing dispatch.

## Definitions

`success_device_count` means that FCM accepted the send request for a device. It
does not prove that the operating system displayed the notification.

`notifications_inbox` is the authoritative per-profile audience record:

- `opened_at` means the profile opened the notification or tapped the push.
- `read_at` means the profile marked the notification as read.
- A null timestamp means that action has not been observed.

The UI will label these facts explicitly and will not call FCM acceptance
"delivered".

## Android Icon

Add an Android drawable based on the existing Aiki circular mark and configure
Firebase Messaging default icon metadata in `AndroidManifest.xml`. Use the
existing Aiki brand color as the notification color. The launcher icon remains
unchanged. Android-specific visual validation will be required because small
notification icons use a monochrome mask.

## Resend Contract

The manual dispatch function will accept a request identifier and one optional
operation target. A completed/partial resend uses a source dispatch UUID; a
failed zero-success retry uses a retry dispatch UUID. The request identifier is
generated by Flutter for each user action and is reused if that request is
retried. The server derives a unique idempotency key from the operation and
request identifier.

For a resend, the source dispatch content/action snapshot is copied into a new
dispatch and the audience is resolved again from the snapshot audience type.
The original dispatch and its inbox rows remain immutable. The new dispatch
gets new inbox rows and its own FCM processing result. The source relationship
uses the existing dispatch source fields; no schema change is required.

For a failed dispatch with zero successes, the existing retry path keeps the
same dispatch and idempotency key. Processing dispatches cannot be resent until
they reach a terminal state.

## Admin Detail

`AdminNotificationDispatchDetailPage` will use the existing AIKI cards, type,
spacing, buttons, and saving overlay. It will contain:

- notification snapshot, audience, destination, status, and timestamps;
- KPI cards for target profiles, eligible devices, FCM accepted, failures, and
  invalid registrations;
- KPI cards for opened, not opened, read, and open/read percentages;
- a per-profile list derived from inbox rows with `Pendiente`, `Abierta`, or
  `Leída` state;
- `Reenviar`, `Reintentar`, or disabled action according to dispatch status.

Because current data has device aggregates but no per-profile FCM outcome, the
profile list will report inbox/open/read state only. FCM metrics remain global
device-level metrics.

## Data Flow

The admin dispatch service will query inbox tracking rows by dispatch using the
existing admin RLS policy. It will resolve profile display data separately and
return typed analytics to Flutter. Local notification inbox sync remains scoped
to the authenticated profile and is not reused for the admin aggregate query.

## Validation

- Edge Function tests for request parsing, idempotency, source snapshot resend,
  retry behavior, and dispatch provenance.
- Flutter tests for analytics decoding, status labels, resend actions, and
  history-card navigation.
- `deno test`, `deno check`, focused Flutter tests, `flutter analyze`, and
  Android debug build.
- Manual Android verification of the Aiki notification icon in background and
  terminated app states.
